# Infinite Experiment — UI Feature Audit & Inventory

**Date:** 2026-05-13
**Scope:** Vizburo dashboard (server-rendered web UI inside the `politburo/` repo). Discord-bot UI (`comrade-bot`) and infra (`labour-bureau`) are referenced only where they intersect with the web UI surface.

---

## 1. Overall Tech Stack

| Layer | Technology |
|---|---|
| Rendering | Go `html/template` (server-side), composed of `layouts/`, `pages/`, `partials/` |
| Interactivity | **HTMX 1.x** (vendored at `/static/js/htmx.min.js`) + vanilla JS modules |
| Styling | Hand-authored CSS in `/static/css/design-system.css` (660 lines) + a separate `/static/css/output.css` (1156 lines) that appears to be a Tailwind build artifact (Tailwind config exists at `vizburo/ui/tailwind.config.js`, but production templates link only `design-system.css`) |
| CSS architecture | CSS custom properties as design tokens (`--bg-app`, `--accent-primary`, `--status-*`, etc.). Heavy use of **inline `style=` attributes** throughout templates. |
| Maps | **Leaflet 1.9.4** loaded from `unpkg.com` CDN (live tracking, logbook). A second map library, **Gleo** (extensive `static/js/gleo/` tree), is shipped but **not referenced by any active template** — appears to be an unused/experimental dependency. |
| Icons | **Lucide** (loaded via `unpkg.com` CDN on map pages); inline SVGs for nav and FAB; emojis for dashboard card icons |
| Routing | Chi router (`internal/routes/router.go`) — server-rendered, no SPA |
| Auth | Session-based UI auth via `session_id` cookie (Redis-backed); created by presigned `/auth/login?token=…` links generated by the Discord bot |
| Multi-tenant | Every authenticated user has 0..N Virtual Airline (VA) memberships; an "active VA" is part of the session and switched in-place via HTMX POST to `/dashboard/switch-va` |

There is **no JavaScript framework, no build step on the critical path, no client-side routing**. The dashboard is a classic HTMX-over-HTML app.

There is a parallel/unused UI tree at `politburo/vizburo/ui/templates/` (24 files) that mirrors the live templates at `politburo/templates/` (37 files). The live binary serves from `politburo/templates/`. The `vizburo/ui/` tree appears to be either a staging area or dead code from an unfinished refactor.

## 2. Global Shell & Navigation

**Layout file:** `politburo/templates/layouts/base.html`

### 2.1 App shell (desktop, ≥ 769 px)

A **two-column grid** (`grid-template-columns: 72px 1fr`, full viewport height):

- **Left rail (`.desktop-tenant-sidebar`, 72 px wide)** — Discord-style vertical strip of circular tenant avatars, one per VA the user belongs to. Top: a static "V" logo block. Bottom: a disabled settings cog with a "Settings coming soon" tooltip. Each avatar shows 2-letter initials derived from the VA name; on hover, a tooltip with the VA name appears (CSS-only `::before`). The active VA gets a colored left-edge bar.
- **Main column** — A "desktop header" partial (`desktop-nav.html`) with the VA name, welcome message, horizontal nav links, and a user avatar circle exists but is **wrapped in `style="display: none;"`** in `base.html`. The desktop top nav is therefore hidden site-wide; navigation happens via the in-page secondary nav.
- **Content area** — `<main>` with `padding: 2rem`, max-width 1280 px, contains `#dashboard-content` which is the HTMX swap target for VA switching.

### 2.2 App shell (mobile, ≤ 768 px)

Driven by media queries plus three partials:

- **`mobile-header.html`** — fixed top bar (64 px), hamburger button on the left, page title in the center.
- **`mobile-drawer.html`** — left-slide drawer (280 px / 75 vw), opened by hamburger, contains menu items from `GetMenuItems`. Backed by `.mobile-overlay` backdrop.
- **`mobile-fab.html`** — bottom-right Floating Action Button showing the active VA's initials. Tapping it fans out a vertical menu of the user's other VAs (with labels exposed via `data-label`), each posting to `/dashboard/switch-va` and then doing a full `window.location.reload()`. Also includes a non-functional "Settings" item.

The hamburger drawer toggle and FAB toggle are wired with **inline `onclick` handlers + global functions** declared in `base.html` (`toggleDrawer`, `closeDrawer`, `toggleFab`, `closeFab`). Outside clicks dismiss them via document-level listeners.

### 2.3 In-page secondary navigation

**Partial:** `templates/partials/secondary-nav.html`. Rendered at the top of every authenticated dashboard page. A horizontal tab strip (`.secondary-nav`) with bottom-border underline for the active page. The menu list is computed in **Go** by `internal/platform/ui/menu.go:GetMenuItems(activeVA)` which filters items by role:

| Item | Path | Required role |
|---|---|---|
| Dashboard | `/dashboard` | Pilot |
| Live Flights | `/dashboard/live` | Pilot |
| Logbook | `/dashboard/logbook` | Airline Manager (staff) |
| VA Admin | `/dashboard/vaadmin` | Admin |
| Datasource | `/dashboard/settings/datasource` | Admin |
| Events | `/dashboard/events` | Admin |

Livery Mappings is reachable from links inside Datasource / Dashboard cards, but is not in the secondary nav.

### 2.4 Global UI elements

- **HTMX global spinner** (`#global-spinner`) — fixed full-screen overlay backdrop + spinner, shown when any HTMX request is in flight (`htmx-indicator` class).
- **`/auth/login?token=…`** — presigned-link landing page. Bot sends a Discord DM with a one-time signed URL; clicking it creates a session and redirects to `/dashboard`.
- **Error pages** — `pages/401.html` (unauthorized; advertises Discord slash commands `/link`, `/live`, `/dashboard` as the way to get a new sign-in link) and `pages/404.html` (also used for 405).

## 3. Pages — Feature by Feature

> File paths below all live under `politburo/`.

### 3.1 Dashboard (`/dashboard`)

**Template:** `templates/pages/dashboard.html` • **Roles:** any member (Pilot+) • **Handler:** `internal/dashboard/`

**What it does:** Landing page after sign-in. Three vertical sections:

1. **Pilot Stats** (`partials/pilot-stats.html`) — a card displaying up to three columns of stats:
   - **Game Stats** — Flight Time, Online Flights, Landings, XP, Grade (from Infinite Flight Live API).
   - **VA Stats** — Flight Hours, Rank, Total Flights, Status, Region, Last Activity, Last Flight, Join Date + arbitrary `AdditionalFields` map (provider-driven, e.g., Airtable columns).
   - **Career Mode** — Total CM Hours, Hours to Next Aircraft, Aircraft, Airline, Assigned Routes, Last Flown Route, Last Activity, plus `AdditionalFields`.
   Each section is conditionally rendered if data exists. No interactivity.
2. **Leaderboard** (only if `.ActiveEvent` is set) — a static table of pilots ranked by PIREP count for the currently active event. Rank 1/2/3 get medal emojis. Each row is clickable; clicking opens a **modal** (`#pilot-logs-modal`) and HTMX-loads `/dashboard/leaderboard/pilot/logs?pilot_at_id=…` into it. The modal is a custom-built overlay (fixed div with `display: flex/none` toggled via inline JS), not a `<dialog>` element.
3. **Feature cards** — grid of 2–6 entry-point cards (Live Flights, Logbook, VA Admin, Datasource, Events, Livery Mappings), filtered by role. Each is a plain `<a>` to the corresponding dashboard route.

**UX patterns:**
- Clickable table rows for the leaderboard with a hover background change.
- Custom modal with manual JS open/close.

**Limitations / gaps:**
- Stats are static at render time — no refresh button, no live update.
- Modal lacks keyboard accessibility (no focus trap, no Esc-to-close wired).
- The leaderboard renders all rows at once; no pagination or filter.

### 3.2 Live Flights (`/dashboard/live`)

**Template:** `templates/pages/live.html` (1632 lines) • **Roles:** any member • **Handler:** `internal/flights/`

**What it does:** Real-time radar view of active flights for the current VA, fed from a Redis cache populated by the flights cache job (every minute).

**Layout:** Card with header + a **split-pane**:
- **Left panel (25 %, desktop only)** — Scrollable list of active flights. Each item shows callsign (truncated with `..` prefix if > 15 chars) and `origin → destination`. Hover and active states highlight via left-edge border.
- **Right panel (75 %)** — A Leaflet map. Flights rendered as **SVG triangle markers rotated to the heading** (track), colored by phase:
  - Cruise → blue
  - Climb → green
  - Descent → purple
  - Takeoff → amber
  - On-ground → slate

**Interactions:**
- Click a list item or a marker → highlights the list row, zooms map to the flight (zoom 10), fetches `/dashboard/flights/{flight_id}/waypoints`, draws a **polyline route colored by altitude** (linear red-at-ground → blue-at-cruise), and pops a **floating flight detail card** at the bottom-left of the map.
- The detail card shows: airline/session name, callsign, phase badge, route strip (`KORD ✈ KLAX`), three big stats (Altitude, Speed, V/S with up/down arrow icon), and a metadata block (aircraft, livery, max altitude/speed, detected-at, last-updated, last-report, flight-plan-fetched timestamps, all formatted in UTC 24-hr).
- Map background click closes the card and clears the route.

**Mobile UX (≤ 768 px):**
- Flight list panel is hidden. Map fills the available space.
- A bottom **"flight list overlay"** (bottom-sheet style with transform animations) is opened by a "Flight List" button that becomes visible once a flight is selected.
- A "View Details" button shows the bottom-sheet flight card.
- Two-step interaction: tap a marker → flight selected (route drawn) but card not auto-opened; tap "View Details" to show the card.

**Technical notes / limitations:**
- All flight data is **passed at render time** via `{{.FlightsJSON}}` injected into a `<script>` block. There is **no auto-refresh** — to see new flights, the user reloads the page.
- Leaflet and Lucide are loaded from **unpkg.com** (third-party CDN; an outage breaks the page).
- The Leaflet map needs **four staggered `invalidateSize()` calls** (0, 100 ms, 500 ms, 1000 ms) to render correctly inside the flex layout — indicates layout fragility.
- Heavy inline JS (~800 lines) inside the template; no module isolation.

### 3.3 Logbook (`/dashboard/logbook`)

**Template:** `templates/pages/logbook.html` (1441 lines) • **Roles:** Staff + Admin • **Handler:** `internal/pilots/`

**What it does:** Staff lookup of any pilot's historical flight log by IFC ID.

**Layout:** Similar split-pane as Live Flights, but the left panel has a search header and pagination at its bottom:
- Header with an **input field** ("IFC ID") + a "Load Logbook" button.
- Left: paginated flight list (HTMX-loaded from `/dashboard/logbook/flights?user_id=…&page=1`).
- Right: map area with three possible states:
  1. **Empty state** — generic "Select a flight to view route" placeholder.
  2. **Map state** — Leaflet map rendered with altitude-colored polyline (same `FlightMap` class as Live Flights) plus a floating detail card.
  3. **Info pane state** — for flights with no waypoints (sparse historical data), the right panel renders a structured info panel showing Flight Details (callsign, start/end time, duration, XP, landings, server, session ID, world type, day/night time, violations), Aircraft, Pilot, plus an amber notice "Map is not available for this flight."

**Interactions:**
- Submit IFC ID via Enter key or button click → HTMX `GET` flushes flight list and updates `?user_id=` in the URL via `pushState` (so the page is deep-linkable).
- Click a flight → fetches waypoints. If ≥ 2 waypoints: initialize map, draw route, show detail card. If < 2 or 404: tear down map, show info pane.
- Pagination buttons in the left panel use HTMX swap with OOB updates to refresh the page counter.
- Close button on the detail card clears route, destroys map instance, and resets to the empty state.

**Detail card fields:** Duration, XP, Landings, Start/End time, Server, Session ID, World Type (1=Casual, 2=Training, 3=Expert), Day/Night Time, Violations (amber-colored), Max Speed/Altitude, Aircraft, Livery.

**Limitations:**
- IFC ID input has no autocomplete / validation / pilot search — operator must type or paste a known ID.
- No date filtering, no aircraft filtering, no route filtering.
- Map instance is destroyed/recreated per flight click rather than reused (performance hit).

### 3.5 Manage Pilots (`/dashboard/vaadmin/pilots`)

**Template:** `templates/pages/vaadmin-pilots.html` + `partials/pilots-table.html` • **Roles:** Admin

**What it does:** Tabular CRUD for VA membership. The table itself is HTMX-loaded into `#pilots-container` on page load.

**Per-row controls:**
- **Callsign cell** — inline form with an input + a save icon button. Submits to `POST /dashboard/vaadmin/pilots/{pilot_id}/callsign`. Pattern attribute restricts input to a regex; invalid input is colored red via `:invalid` selector.
- **Role badge** — colored pill (`role-pilot` blue / `role-staff` green / `role-admin` red).
- **Role select** — `<select>` posting to `POST /dashboard/vaadmin/pilots/{pilot_id}/role`.
- **Remove button** — `DELETE /dashboard/vaadmin/pilots/{pilot_id}`, styled in danger red.

**Limitations:**
- No search/filter/sort on the table; all pilots rendered at once.
- No empty-state CTA to invite or onboard.

### 3.6 Flight Modes (`/dashboard/vaadmin/flight-modes`)

**Template:** `templates/pages/vaadmin-flight-modes.html` + `partials/flight-modes-list.html` + `partials/flight-mode-edit-form.html`

**What it does:** Configure which PIREP submission modes (e.g., "career mode", "regular", custom IDs) are enabled and which form fields are shown for each. Modes render as a grid of "mode cards", each with:
- Mode ID (monospace, accent color).
- Enabled/disabled status badge.
- Toggle button (`POST /dashboard/vaadmin/flight-modes/{mode_id}/toggle`) — flips state in place via HTMX.
- Edit button (`GET /dashboard/vaadmin/flight-modes/{mode_id}/edit`) → loads edit form partial inline.

The edit form lets admins customize which fields are visible/required and per-field labels for the in-Discord PIREP modal.

### 3.7 Webhooks (`/dashboard/vaadmin/webhooks`)

**Template:** `templates/pages/vaadmin-webhooks.html` + `partials/webhooks-list.html`

**What it does:** Configure Discord webhook integrations that post live-flight snapshots to a Discord channel every 30 minutes.

**Features:**
- List existing webhooks (channel, type, last-run timestamp).
- Add webhook form (`POST /dashboard/vaadmin/webhooks`) — accepts a Discord webhook URL.
- **"Run now"** button (`POST /dashboard/vaadmin/webhooks/run`) — triggers an immediate snapshot post. Server responds with an `HX-Trigger: webhookRunResult` event, and a small inline script writes a transient success/error message to `#webhook-run-feedback` for 5 seconds.

This is the only place in the app that uses `HX-Trigger` for an out-of-band status message.

### 3.8 Events (`/dashboard/events`)

**Template:** `templates/pages/events.html` + 4 partials • **Roles:** Admin

**What it does:** Tour/event management — admins create multi-leg events (tours), each with multiple legs (per-leg origin/destination, scoring multipliers, etc.).

**Page structure:**
- Header with "+ Create Event" button → HTMX-loads `event-form` into `#event-form-container`.
- Events table list (`#events-container`) auto-loads on page load and refreshes on custom body events: `eventCreated`, `eventUpdated`, `eventDeleted`.
- A separate `#leg-form-container` for managing legs of an expanded event.

**Event row behavior:**
- Status badge (Draft / Active / Completed / Cancelled) with color coding.
- Click a row → toggles a nested "legs" row.
- Per-row action buttons (Edit, Delete, Change Status).

**Route autocomplete (only inline-autocomplete UX in the entire app):**
- Route-id input in the leg form uses `hx-trigger="keyup changed delay:500ms"` posting to `/dashboard/events/routes/search`.
- Results render into a dropdown of route cards (route code, origin → destination, ATID), each clickable to populate hidden fields via `selectRoute(...)`.

**Limitations:**
- No bulk operations on events or legs.
- No copy/duplicate, no archive flow.
- The `toggleEventLegs` function does direct DOM manipulation by ID — fragile if the list is re-rendered.

### 3.9 Datasource Configuration (`/dashboard/settings/datasource`)

**Template:** `templates/pages/datasource.html` + 6 partials • **Roles:** Admin

**What it does:** Wizard for configuring an Airtable backend per VA. The single `#datasource-status-container` swaps between several states based on what's configured.

**State machine:**
1. **No credentials** → empty-state card with an SVG box icon, a "Setup Datasource" CTA (loads type-selector), and a link to Aircraft & Livery Mappings.
2. **Credentials saved, no schemas** → "Credentials Configured" status block + "Configure Schemas" CTA (loads schema-selector).
3. **Fully configured** → list of configured schemas as cards (each with Enabled/Disabled badge and an "Edit Schema" button), plus Edit Credentials and Add Schema buttons.

**Sub-flows:**
- **Credentials form** — API key, base ID; tested via `POST /dashboard/settings/datasource/test-connection`.
- **Schema selector** — pick which logical schema to map (pilots, routes, pireps, career mode).
- **Schema config** + **field mapper** — for each schema, map IF/internal field names to Airtable column names; also includes a "Sync from Airtable" button.

**Limitations:**
- Only Airtable is supported despite the "type-selector" abstraction.
- No diff/preview before applying a schema change.
- No history of past syncs visible from the UI.
- The schema-config flow is dense and not progressively disclosed — admins see all fields at once.

### 3.10 Aircraft & Livery Mappings (`/dashboard/settings/livery-mappings`)

**Template:** `templates/pages/livery-mappings.html` • **Roles:** Admin

**What it does:** Maps Infinite Flight's aircraft/livery names to the VA's standardized labels for PIREP submission. Two tabs ("Aircraft", "Airline") render two separate sortable lists.

**Features:**
- **Defaults form** — Set fallback Default Aircraft and Default Airline. `loadDefaults()` / `saveDefaults()` via `fetch()` to `/api/v1/admin/livery-mappings/defaults`.
- **Add Mapping form** — Field type select (aircraft / airline), source value with `<datalist>` autocomplete (populated from `/api/v1/admin/livery-mappings/unique-aircraft` or `/unique-liveries`), target value.
- **Mappings table** — Two tab panels with rows showing Livery name (truncated), Source Value (IF), Target Value (VA), and Delete button. JavaScript-only tab switching.

**Unique pattern:** All AJAX is plain `fetch()`, not HTMX — the only major dashboard page that diverges from HTMX.

**Limitations:**
- No bulk import / CSV upload despite the obvious need (hundreds of liveries).
- `alert()` and `confirm()` are used for messaging.
- No search box.
- No edit — only Delete + re-add.

## 4. Cross-Cutting Patterns & Components

### 4.1 Cards
`.card` class — `bg-surface`, subtle border, 0.5 rem radius, padding 1.5 rem, hover lifts border + adds a soft blue glow. Used as the container for nearly every page section.

### 4.2 Buttons
- `.btn-primary` — accent blue, white text.
- `.btn-secondary` — surface bg, bordered.
- Custom `btn-create-event`, `.btn-action`, `.btn-remove`, `.btn-danger`, mobile-only `.mobile-button` — variants defined per template.
- `min-height: 44px` enforced for touch on the global `.btn`.

### 4.3 Forms
- Dark inputs (`--bg-sidebar` fill, slate border, focuses to accent blue with an 8 px halo).
- Form labels are 0.875 rem, semibold, slate-100.
- Validation is server-side; client-side feedback is via inline messages added/removed by inline JS (no shared component).

### 4.4 Tables
- Common pattern: dark header strip, slate-divided rows, hover background `rgba(255,255,255,0.03)`, uppercase th text with letter-spacing.
- No virtualization; all rows rendered server-side.
- Sort/filter UI exists only ad hoc.

### 4.5 Badges
- Status badges (Draft, Active, Completed, Cancelled), Role badges (Pilot, Staff, Admin), Phase badges (Cruise, Climb, Descent, Takeoff, On Ground, Landed, Unknown), Schema state (Enabled, Disabled, ACTIVE).
- Color convention: green = good/active, blue = info, amber = warning, purple = info-2, red = danger/error, slate = neutral.

### 4.6 Modals & Overlays
**No shared modal component.** Three different patterns coexist:
1. Pilot-logs modal on the dashboard — custom fixed div toggled via inline `style.display`.
2. Live Flights mobile flight list — full-screen overlay with bottom-sheet animation.
3. Logbook flight info pane — replaces map area in place (not actually a modal).

None have focus trap, Esc-to-close, or aria attributes.

### 4.7 HTMX usage conventions
- Heavy use of `hx-target` + `hx-swap="innerHTML"` to swap into a stable container.
- Common page-load fetches: `hx-trigger="load"` on the partial container so the page shell renders immediately and the data loads after.
- Cross-component refresh uses **custom body events** (`eventCreated`, `eventUpdated`, `eventDeleted`, `credentials-saved`, `schema-saved`, `webhookRunResult`) — fired via `HX-Trigger` response headers and listened to via `hx-trigger="<name> from:body"`.
- **No polling** — there is no `hx-trigger="every Xs"` anywhere. All refreshes are user-initiated or event-driven.

### 4.8 JavaScript distribution
- A few module files: `flight-map.mjs`, `gleo-bridge.mjs`, `map-route-utils.mjs` (Live Flights / Logbook only).
- Vast majority of behavior is **inline `<script>` blocks per template**.
- Global functions (`toggleDrawer`, `closeFab`, `toggleEventLegs`, `loadLogbook`, `focusFlightOnMap`, `closeFlightCard`, `selectRoute`, `switchTab`, `deleteMapping`, `loadMappings`, ...) attached to `window` for inter-template references.

## 5. Responsive Design Status

| Breakpoint | Effect |
|---|---|
| `>768 px` | Full app shell: left rail + main content. Desktop header partial exists but is hidden by an inline `display:none` (so the only nav visible is the in-page secondary nav). |
| `≤768 px` | App shell collapses; mobile header + drawer + FAB appear. Live Flights and Logbook reflow to single-column map + bottom-sheet UX. Pilots table action buttons stack vertically. |
| `≤640 px` | Logbook input section stacks vertically; flight list panel max-height shrinks. |

**Strengths:** A real mobile path is implemented for the two most data-dense pages (Live Flights, Logbook). Touch targets meet 44 px minimum. Bottom-sheet pattern is used appropriately.

**Weaknesses:**
- The desktop top nav is dead code — VA name & user avatar only appear on mobile. Desktop users never see their own username.
- Some pages (Events, Datasource, Livery Mappings) rely on tables/forms that get cramped on phones with no special mobile treatment.
- No tablet-specific breakpoint; behavior between 640 and 768 px is the desktop layout, which is borderline at narrow widths.

## 6. Authentication & Access Control on UI Pages

- **Sign-in:** Bot generates a presigned `/auth/login?token=…` URL signed via JWT secret. Visiting it creates a Redis-backed session and sets a `session_id` cookie.
- **`uiAuthMiddleware`** (`routes/router.go`): for every `/dashboard/*` route, checks the session, expiry, and presence of an `ActiveVA`. If any check fails, renders the 401 page (which advertises Discord slash commands as the way back in).
- **Role gates inside `/dashboard`:**
  - Pilot+ (default group): `/dashboard`, `/dashboard/live`, `/dashboard/leaderboard/pilot/logs`, `/dashboard/flights/{id}/waypoints`
  - Staff+ (`IsStaffMiddleware`): `/dashboard/logbook`, `/dashboard/logbook/flights`
  - Admin (`IsAdminMiddleware`): `/dashboard/vaadmin/*`, `/dashboard/events/*`, `/dashboard/settings/datasource/*`, `/dashboard/settings/livery-mappings`
- **No self-service signup in the UI.** All onboarding (pilot registration, VA join, server init) goes through Discord slash commands.
- **No logout flow in the UI.** No "sign out" button anywhere; session expires on the server side.

## 7. Known Technical Limitations & Gaps

1. **VA-switch route is referenced but not registered.** Both `base.html` and `mobile-fab.html` POST to `/dashboard/switch-va`, but the route does not exist in `internal/routes/router.go`. Either a regression or a handler wired elsewhere.

2. **Desktop top header is hidden globally** (`style="display: none;"` around the `desktop-nav` include in `base.html`). The username and VA name are visible only on mobile — desktop users navigate by the in-page secondary nav only. There is no profile menu, no logout, no settings.

3. **Inline styles everywhere.** Every page contains a `<style>` block with page-specific rules. Many elements use `style="..."` attributes directly. The "design system" CSS provides tokens and base components, but page-level styling is hand-rolled per template.

4. **CSS duplication.** `design-system.css` (660 lines, hand-authored) and `output.css` (1156 lines, Tailwind build artifact) both exist; production templates link only the former. The Tailwind toolchain is present but appears unused by the live binary.

5. **Two map libraries.** Leaflet (used) and Gleo (vendored under `static/js/gleo/` with ~60 files but not referenced by any live template).

6. **No client-side state library.** All page state is in the DOM and in `window` globals. Cross-page communication is via custom HTMX/body events. Works, but is fragile when a partial is re-rendered (e.g., active highlights are lost if not re-applied).

7. **Modals are inconsistent.** Three different overlay patterns. None accessible by keyboard.

8. **No shared notification / toast system.** Success/error messages are either:
   - `alert()` (livery mappings)
   - Inline timed `setTimeout` clears (webhooks "Run now")
   - Inline static divs (datasource forms)
   - or silent (most HTMX swaps assume success means a swap happened)

9. **No loading skeletons or progressive disclosure.** The global spinner is the only loading affordance; partials show generic `Loading…` text while loading.

10. **No theming.** Dark theme is hard-coded. No light-mode toggle, no high-contrast mode, even though the design tokens are all CSS variables and a switch would be trivial.

11. **Accessibility gaps:** No `aria-label` on most interactive icons; SVGs lack `<title>` elements; modal dialogs are not actual `<dialog>` elements; tab interfaces don't follow `role="tablist"` semantics; color is the sole indicator for status/phase badges.

12. **Third-party CDN dependency.** Leaflet + Lucide are pulled from `unpkg.com` at runtime on the two map pages. An unpkg outage takes down the radar and logbook.

13. **Large template files.** `live.html` is 1632 lines and `logbook.html` is 1441 lines — much of this is inline JS and CSS that would benefit from extraction.

## 8. Discord-Bot Surface (Context, Not UI)

Although outside the web-UI scope, the bot is the **primary entry point** to every web feature. Pages such as `pages/401.html` direct users back to these slash commands when they need to (re)authenticate. The bot in `comrade-bot/src/commands/` exposes:

`/register`, `/membership`, `/initServer`, `/configure`, `/pilot`, `/stats`, `/status`, `/log`, `/logbook`, `/live`, `/dashboard`, `/events`, `/tour`, `/tour_leg`, `/help`, `/rollout`

The bot uses Discord modals + buttons for data input that does not have a corresponding web flow. Most notably, **filing a PIREP and joining a VA are Discord-only flows** — they exist only as Discord interactions today, not as web pages.

## 9. Suggested Designer Reading Order

If a designer is being onboarded to redesign this UI, the most efficient path is:

1. `politburo/static/css/design-system.css` — current tokens, colors, components.
2. `politburo/templates/layouts/base.html` — global shell.
3. `politburo/templates/pages/dashboard.html` — the landing page.
4. `politburo/templates/pages/live.html` — the most complex interactive page.
5. `politburo/templates/pages/logbook.html` — second-most-complex; close cousin of Live Flights.
6. `politburo/templates/pages/events.html` + `partials/event-form.html` + `partials/event-leg-form.html` — admin form-heavy flow.
7. `politburo/templates/pages/livery-mappings.html` — the "outlier" page that mixes paradigms.
8. `politburo/internal/platform/ui/menu.go` — role-driven navigation source of truth.

These eight files cover roughly 90% of what a user ever sees in the product.
